# 자동완성을 넘어 개발 루프로: Codex와 만든 ONE ROPE

ONE ROPE는 로프로 붕괴 도시를 올라가는 Canvas 기반 2D 액션 로그라이크입니다. 고정 길이 로프를 이용한 진자 운동, 전투와 증강, 6개 Sector의 48개 Stage, 보스전, 모바일 조작과 WebSocket 협동 플레이까지 구현했습니다.

이 과정에서 Codex는 단순히 코드를 생성하는 도구가 아니었습니다. 사람이 게임의 방향과 합격 기준을 결정하면, Codex가 그 결정을 코드·데이터·문서·검증으로 연결하는 실행 파트너 역할을 맡았습니다.

## Codex를 어디에 사용했나요?

Codex는 기획 이후의 개발 전 과정에 사용했습니다.

먼저 대화로 정한 요구사항이 기존 코드의 어느 부분에 영향을 주는지 분석했습니다. 이후 작업을 GitHub Issue와 전용 브랜치로 나누고, 코드와 기준 문서를 함께 수정했습니다. 구현이 끝나면 validator, 브라우저 플레이, 실제 WebSocket 연결을 통해 결과를 확인하고 PR에 검증 범위와 미검증 항목을 기록했습니다.

작업 흐름은 다음과 같았습니다.

> 사람의 결정 → Codex의 영향 범위 분석 → Issue·Worktree 분리 → 구현과 문서 정렬 → Validator·브라우저·멀티플레이 검증 → PR 병합

서로 독립적인 작업은 여러 Codex 작업과 Git Worktree로 나눠 병렬로 진행했습니다. 한 작업이 기능을 구현하면 다른 작업은 기존 계약과 충돌하지 않는지 확인하는 방식으로 속도와 안정성을 함께 확보했습니다.

또한 `AGENTS.md`에는 반복해서 적용할 개발 원칙을, 기준 문서에는 현재 제품과 아키텍처 결정을 기록했습니다. 덕분에 새 Codex 작업을 시작해도 이전 대화의 의도를 다시 설명하지 않고 같은 기준에서 개발을 이어갈 수 있었습니다.

## 어떤 기능을 구현했나요?

가장 먼저 완성한 것은 게임의 핵심인 로프 액션입니다.

초기 로프는 탄성 때문에 입력하지 않아도 캐릭터가 가속되는 문제가 있었습니다. 플레이어가 자신의 조작과 결과 사이의 인과관계를 느끼기 어려웠습니다. 사람은 “로프 길이는 고정하고, 가속은 플레이어가 선택한 접선 방향 드래그에서만 발생한다”는 조작 원칙을 결정했습니다.

Codex는 이를 고정 길이 제약, 접선 방향 충격, 중력, 해제 관성으로 나누어 구현했습니다. 이후 PC와 모바일 입력이 같은 로프 명령을 사용하도록 통합하고, 발사 중인 Hook과 부착·실패·재사용 대기시간까지 하나의 수명주기로 정리했습니다.

그 위에 다음 기능을 확장했습니다.

- 6개 Sector, 48개 Stage로 구성된 연속 수직 월드
- 적 처치 경험치와 증강·마법 성장
- 추격·방패·포격·지원·군집형 Enemy
- Boss03과 Boss06 전투 및 탈출 연출
- 플레이어별 체크포인트와 사망·낙사 복구
- 모바일 조작, PWA 설치와 원격 실행
- WebSocket 기반 협동 플레이와 상태 동기화
- 전투 VFX, 스프라이트·환경·오디오 교체 파이프라인
- Stage를 직접 편집하고 Runtime으로 변환하는 Map Editor

## 어떤 문제를 해결했나요?

### 커지는 조건문을 객체 구조로 바꿨습니다

기능이 늘어나자 하나의 상위 함수가 Enemy 종류, 상태, 투사체, 피드백을 모두 조건문으로 구분하기 시작했습니다. 같은 물리 계산과 문자열 ID도 여러 위치에 반복됐습니다.

사람은 “플레이어가 게임에서 하나의 객체로 인식하는 단위와 코드의 책임 단위가 같아야 한다”는 구조를 결정했습니다.

Codex는 공통 정체성은 상위 클래스, 독립된 상태는 Has-A 컴포넌트, 여러 객체가 선택적으로 공유하는 능력은 Mixin으로 분리했습니다. Player·Enemy·Projectile은 공통 Physics 계약을 사용하고, 회전·지형 충돌·유도·수명주기처럼 필요한 능력만 조합하도록 바꿨습니다.

새 Enemy를 추가할 때 중앙 조건문을 수정하는 대신, 해당 Enemy의 Behavior와 상태 구현을 추가할 수 있는 구조가 됐습니다.

### 멀티플레이 지연과 상태 되감기를 해결했습니다

모든 행동을 서버 확인 이후 실행하면 모바일 환경에서 이동, 로프, 피격 반응이 네트워크 왕복 시간만큼 늦어집니다. 반대로 클라이언트가 모든 것을 결정하면 Enemy와 공용 월드 상태가 서로 달라질 수 있습니다.

이를 해결하기 위해 권한을 객체의 상태 변화 원인에 따라 나눴습니다.

플레이어와 로프처럼 입력에 반응하는 객체는 소유 클라이언트가 즉시 처리합니다. Enemy, 적 투사체, 공용 월드는 서버가 진행합니다. 피해는 피해 클라이언트가 먼저 반응하고 서버가 사건을 검증해 다른 플레이어에게 공유합니다.

Codex는 이 원칙을 로컬 예측, 원격 보간, 사건 중복 제거, 상태 지문 기반 복구로 구현했습니다. 덕분에 조작 반응은 서버 응답을 기다리지 않으면서도 최종 상태는 참가자 사이에서 수렴합니다.

### 기획 문서와 실제 맵이 달라지는 문제를 막았습니다

Stage가 늘어나면서 문서의 좌표, 에디터 미리보기, 실제 충돌 지형이 서로 달라질 위험이 커졌습니다.

사람은 Map Editor의 `AREA-SPEC.v2.json`을 Stage 공간의 단일 권위로 사용하기로 결정했습니다. Codex는 이를 편집기, compiler, Runtime catalog와 연결하고 48개 Stage 및 47개 전환 포탈의 일치 여부를 검사하는 validator를 만들었습니다.

이제 Runtime이 에디터에 없는 지형을 임의로 추가할 수 없고, 원본과 생성 결과가 달라지면 검증 단계에서 바로 발견됩니다.

자산도 같은 방식으로 처리했습니다. 이미지 생성 도구의 출력 형식을 게임 코드에 직접 연결하지 않고, 스프라이트·환경·오디오를 도구 중립적인 manifest로 정규화했습니다. 자산을 교체해도 물리, 충돌, 전투 코드가 함께 바뀌지 않도록 경계를 분리했습니다.

## 사람이 직접 결정한 부분은 무엇인가요?

Codex가 구현 속도를 높였지만, 게임의 방향을 결정하지는 않았습니다.

사람은 다음 내용을 직접 결정했습니다.

- 로프 숙련이 게임의 중심이라는 제품 방향
- 자동 가속을 제거한 고정 길이 로프의 조작 감각과 수치
- Stage 동선, Enemy 역할, 보스 공격과 연출
- 클래스·컴포넌트·Mixin을 나누는 설계 원칙
- 플레이어와 서버가 각각 어떤 상태를 소유할지에 대한 권한 모델
- 아트 방향과 실제 게임에 사용할 자산의 승인
- 기능의 우선순위와 플레이테스트의 최종 합격 여부

Codex는 대안을 비교하고, 선택된 결정을 저장소 전체에 적용하며, 실제로 동작하는지 검증했습니다. 최종 판단은 언제나 사람이 내렸습니다.

## Codex를 사용하며 얻은 결론

Codex의 가장 큰 장점은 코드를 빠르게 작성하는 능력만이 아니었습니다. 하나의 결정을 관련 코드, 호출자, 멀티플레이 경로, 문서와 검증 도구까지 추적해 일관된 결과로 만드는 능력이 더 중요했습니다.

저희는 Codex에게 아이디어를 대신 맡기지 않았습니다. 사람이 “어떤 게임이어야 하는가”를 결정하고, Codex가 그 의도를 실행 가능한 구조로 끝까지 연결했습니다.

그 결과 만든 것은 게임 하나만이 아닙니다. 사람의 판단을 빠르게 구현하고, 재현하고, 다시 개선할 수 있는 개발 루프까지 함께 만들었습니다.
