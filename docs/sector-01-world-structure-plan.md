# Sector 01 연속 월드 구조 계획

작성일: 2026-08-14

상태: 기획 결정 반영 완료, authored mock 구현 진행 중

제품 기준: [`game-hackathon-planning.md`](./game-hackathon-planning.md)

영역별 기준: [`bsh/scenario/`](./bsh/scenario/)

게임 오브젝트 인계 기준: [`sector-01-game-object-catalog.md`](./sector-01-game-object-catalog.md)

구현 범위는 날짜별 부분 착수가 아니라 현재 시나리오가 확정된 `1-1`~`1-8` 전체 mock 연결이다. 각 영역을 구현할 때 지형·회복 지점·오브젝트·상태·완료 목표·Gate·그래픽/오디오 cue를 게임 오브젝트 카탈로그와 runtime area definition에 동시에 정리한다. 구현 중 `git status`와 최신 `origin/main`의 시나리오 변경을 확인하고, 좌표·cue 조정은 계속 흡수하되 맵 순서·핵심 기믹·완료 조건·Gate 연결이 바뀌는 큰 방향 전환은 사용자 검토 뒤 반영한다.

맵 definition은 이미지·음원 파일 경로, atlas frame, WAV clip을 소유하지 않는다. 지형은 선택된 environment runtime package가 기존 collision surface 위에 표현하고, 오브젝트와 사건은 stable object/state/event ID만 공개한다. bootstrap에서 검증된 production package를 주입하며 준비되지 않았으면 `default-mock` environment/audio package를 사용한다. 정식 리소스 교체가 맵 좌표·물리·완료 조건·네트워크 상태를 바꾸면 안 된다.

수동 좌표 수정은 사각형의 암묵적 좌상단이 아니라 `coordinateAnchor`가 가리키는 부착점을 기준으로 한다. 수평 발판은 보행면 `top-center`, 바닥에 선 Gate·패널은 `bottom-center`, 천장 부착 구조는 `top-center`, 자유 배치 표식은 `center`를 사용한다. Gate·패널의 바닥 기준점은 실제 발판 `topY`와 일치해야 하며 층별 렌더 오프셋으로 맞추지 않는다.

로컬 실행과 네트워크 실행은 서로 다른 맵·게임플레이 구현이 아니다. 둘 다 `GameSimulationFactory`가 만든 같은 `GameSimulation`과 현재 authored catalog를 사용한다. 네트워크 경로는 새 맵을 만들지 않고 서버 스냅샷의 동일 world revision과 공용 진행 상태를 검증·복원한다. 실행 방식에 따라 월드 catalog를 따로 선택하지 않는다.

## 목적

현재 시드 기반 48단계 수직 월드 프로토타입을 한 번에 폐기하지 않으면서, `SECTOR 01`의 저작 시나리오를 **하나의 붕괴 도시 월드 안에 이어지는 진행 영역**으로 구현한다. 이 문서는 기획자에게는 영역 사이의 연결·완료 조건을, 메인 개발자에게는 구현 선행 관계와 완료 기준을 공유하는 기준이다.

## 확정된 기획 결정

- 실제 월드는 하나다. `1-1`, `1-2` 같은 맵 번호는 별도로 로드되는 월드나 독립 게임 세션이 아니라 같은 월드 안의 진행 영역이다.
- 로컬·네트워크 실행은 같은 월드 정의·진행 규칙·오브젝트 상태를 사용한다. 차이는 입력 전달과 권위 상태 복제뿐이며 맵을 별도로 구현하지 않는다.
- 각 영역은 현재 영역의 문제를 처리한 뒤 명시적 출구를 통과해야 다음 영역으로 넘어간다.
- 각 영역은 하나의 연속 월드 안에서도 시나리오가 정한 방·Shaft·Atrium의 공간 단위로 읽혀야 한다. runtime `area.bounds`를 좌우 벽체와 층간 벌크헤드의 기준으로 사용하고, Gate는 벌크헤드 개구부에 결합한다. 다만 `areaId`와 방 구분은 UI·완료 조건·현재 목표 같은 게임 진행 상태를 위한 논리 단위이며 별도 물리 월드나 멀티플레이 권한 구역이 아니다. 영역마다 별도 scene이나 world를 로드하지 않지만, 플레이어 중심이 바닥 기준 Gate 문 내부 aperture에 직접 들어온 경우만 같은 월드 좌표계 안에서 다음 영역 입구로 위치를 넘기는 포탈 전이다. 문 위·옆 공간과 벌크헤드 개구부 전체는 포탈 판정에 포함하지 않는다.
- 문제 처리는 적 처치만 뜻하지 않는다. 시나리오에 따라 처치·무력화·우회·상호작용·이동 달성·증강 선택이 완료 조건이 될 수 있다.
- 영역별 완료 조건은 문 옆 Gate 패널을 `blocked → ready`로 바꾸는 선행 조건이다. 플레이어가 ready 패널을 조작해야 Gate가 열리며, 모든 층에서 실제 문 개방 입력은 이 방식으로 통일한다.
- 각 영역의 좌우 경계는 고정 충돌 벽으로 닫고, 각 층 경계는 개구부 없는 전폭 고정 충돌 격벽으로 완전히 봉쇄한다(층별 격리). Gate 잠금은 물리 barrier 없이 공용 진행 상태로만 적용되며, 잠금 중에는 crossing·포탈 전이가 일어나지 않는다. 열린 뒤에도 문이 아닌 위치로 로프 탄성 월경을 허용하지 않는다.
- 출구는 붕괴 도시 탈출의 방향, 현재 영역 완료, 다음 영역 진입을 플레이어에게 명확히 보여주는 장치다.
- 첫 활성 플레이어가 열린 Gate 내부 aperture에 진입하면 공용 영역 진행을 한 번 확정하고 그 플레이어만 다음 영역 입구의 지정 위치로 옮긴다. 문 위를 로프로 지나거나 문 옆에 닿는 동안에는 이동·로프 상태를 유지하고, 실제 문 내부 진입 때만 포탈 초기화를 적용한다. 문은 이후에도 지속 단방향 포탈로 유지되며, 뒤에 남은 플레이어는 같은 문 안에 직접 들어온 시점에 각각 이동하고 공용 진행을 다시 올리지 않는다. 각 진입자의 위치·속도·회전·접지·로프·포인터 버퍼·일시 전투 타이머와 무기 재사용 대기는 초기 상태로 되돌리되, 월드·런·체력·생명·Foundation·무기 수치·체크포인트·공용 오브젝트 진행 상태는 유지한다.
- 그래픽·오디오는 mock으로 먼저 연결한다. 정식 리소스는 영역별 오브젝트·상태·표현 cue 목록을 이어받아 병행 제작한다.
- `1-1`~`1-8` 일반 구간은 하나의 Sector 01 총 타이머를 공유한다. 개별 영역 진입 때 시간을 초기화하지 않는다.
- 명시적 Gate 통과가 일반 시간을 보충하며, 0초부터 하층 붕괴가 상승한다. 붕괴에 잡힌 플레이어는 최소 관전 상태가 되고 다음 Gate에서 자동 합류하며 전원 탈락 때만 Sector 01 일반 구간을 재시작한다.
- 각 섹터에는 보스가 1개씩 있다. 기획자가 정한 보스 진입 지점에서 일반 타이머와 붕괴를 종료하고 잔여 시간을 폐기한 뒤 별도의 보스 전투 타이머를 시작한다.
- 보스 타이머 0초부터 Arena가 붕괴하고 전원 탈락 시 보스 시도만 재시작한다. 보스 처치 뒤 다음 섹터에 진입하면 새 일반 타이머를 시작한다.
- 정확한 시간·Gate 보충량·붕괴 속도는 mock으로 구현한 뒤 공동 플레이로 조정한다. 상세 흐름은 [`sector-timer-and-boss-flow.md`](./sector-timer-and-boss-flow.md)를 따른다.
- 다음 Sector의 Patrol Drone은 별도 맵 전용 적이 아니라 기존 `EnemyObject`의 선택적 Patrol capability다. 맵은 corridor/route와 activation band만 소유하고 공격 FSM·투사체는 재사용한다. Patrol이 없는 Sentry는 기존 정지 동작을 유지한다.

## 아직 정해야 하는 기획

다음 항목은 일반 타이머·붕괴·최소 관전의 mock 구현을 막지 않는다. 다만 최종 밸런스와 보스 구현 또는 Sector 01 전체 완료 선언 전에 확정해야 한다.

1. Sector 01 일반 시간·Gate 보충량·일반 붕괴 속도의 최종값은 얼마인가.
2. 타이머와 탈락 상태의 네트워크 권위·이탈·재접속을 어떻게 처리하는가.
3. Sector 01 보스가 `1-8`·일반 구간 종료 Checkpoint·`2-1` 사이 어디에 위치하고 어떤 순서로 전환되는가.
4. Sector 01 보스의 정체·전투 목표·Phase·완료 조건·표현 cue·보상은 무엇인가.
5. Sector 01 보스 시간과 Arena 붕괴 속도의 최종값은 얼마인가.
6. 최소 관전 HUD와 타이머·붕괴 경고의 최종 그래픽·오디오 cue는 무엇인가.

메인 개발자는 명시적인 mock 수치로 일반 타이머 흐름을 먼저 구현하고, 팀과 기획자가 실제 플레이로 최종 수치를 조정한다. 보스 위치·전투 시나리오는 기획자가 확정하기 전 추정 구현하지 않는다.

| 진행 Phase | 확정된 방향 | 아직 정할 내용 |
| --- | --- | --- |

| 일반 구간 | 영역 사이에서도 계속 감소하고 명시적 Gate 통과 때 시간을 보충한다. 0초부터 하층 붕괴가 상승하며 탈락자는 다음 Gate에 합류한다 | 최종 시간·보충량·붕괴 속도, 네트워크·재접속, 최종 cue |

| 보스 전투 | 별도 보스 타이머를 사용하고 0초부터 Arena가 붕괴한다. 전원 탈락은 보스 시도만 초기화한다 | 보스 시나리오, 최종 시간·붕괴 속도·cue |
| 보스 처치 | 다음 섹터로 진행한다 | Checkpoint·보상·연출과 다음 섹터 진입 순서 |
| 다음 섹터 | 새 섹터의 일반 구간 타이머를 시작한다 | 전환 표현 |

`1-8 CONTAINMENT GATE`는 Sector 01의 일반 구간 최종 종합 Stage이며 이 Stage 자체에는 Boss를 추가하지 않는다. Sector 01 전체 완료는 별도 보스 전투의 위치와 시나리오가 확정된 뒤 정의한다.

## 공용 구조 용어

| 용어 | 의미 | 상태 수명 |
| --- | --- | --- |
| 월드 | 한 런 동안 유지되는 붕괴 도시 전체 | 런 시작부터 종료까지 |
| 섹터 | 일정·시나리오·제작 인계 단위. 영역 8개 묶음 | 월드 안의 진행 묶음 |
| 진행 영역 | 시나리오의 개별 맵. 입구·경로·완료 조건·출구를 가진다 | 월드 안에서 유지 |
| 완료 조건 | Gate 패널을 활성화하기 위해 필요한 목표 집합 | 영역별 |
| Gate 패널 | 선행 목표 뒤 활성화되며 모든 층에서 같은 interaction으로 문을 여는 출구 설비 | 영역별 objective |
| 출구 | Gate 패널 조작 뒤 열리고 다음 영역으로 진행시키는 명시적 Gate | 월드 공용 진행 상태 |
| 표현 cue | 그래픽·오디오·UI 담당자에게 넘길 교체 가능한 표현 요구 | gameplay 상태를 소유하지 않음 |

시나리오 문서의 `Anchor A–D` 표기는 레벨 흐름을 설명하는 랜드마크다. 현재 게임의 “사거리 안 모든 유효 지형 표면에 로프 부착” 규칙을 전용 앵커만 부착 가능한 규칙으로 바꾸지 않는다.

## 예상 코드 경계

구현 때 최종 파일명은 기존 패턴에 맞춰 조정할 수 있지만 책임은 다음처럼 분리한다.

- `src/game/world/WorldGenerator.js`: 현재 시드 월드 생성 진입점을 호환 조립 경계로 유지한다.
- `src/game/world/areas/`: 저작 영역 정의와 Sector 01 catalog를 둔다.
- `src/game/world/`: 영역 연결·참조·통과 가능성을 검증하는 assembler/validator를 둔다.
- `src/game/simulation/GameSimulation.js`: 하나의 월드 수명주기와 진행 상태를 조립하되 영역별 오브젝트 종류를 직접 분기하지 않는다.
- 영역 완료·Gate 상태를 맡는 공용 진행 객체: 구체 Terminal·Sentry·Wind 구현 대신 안정적인 목표 ID와 완료 사건을 집계한다.
- renderer·audio binding: gameplay 상태가 공개한 영역·Gate·오브젝트 사건을 cue로 표현하며 규칙을 소유하지 않는다.
- 네트워크 snapshot: 같은 simulation의 공용 월드 진행·Gate·타이머·붕괴·탈락 상태를 공유하되 구체 권위와 재접속 규칙은 구현 설계에서 확정하고, 별도 네트워크용 맵이나 영역 전환용 새 world seed를 만들지 않는다.

## 테스트 가능한 완료 기준

1. `1-1` Gate는 Service Terminal 상호작용 뒤 이동을 허용하는 0.9초 문구 세 개의 공용 Sequence가 끝나기 전에는 열리지 않고, 완료 후 플레이어가 직접 통과해야 `1-2`가 활성화된다. 최초 플레이 90~120초 목표는 실제 영역 시간 표본으로 검증하고 강제 대기시간으로 만들지 않는다.
2. 첫 Gate 진입자는 자기만 다음 영역 입구의 지정 위치로 이동하며, 뒤의 플레이어는 열린 문 안에 직접 들어온 시점에 각각 이동한다. 각 진입자의 로프·속도·회전·접지·입력 버퍼·일시 전투 상태는 초기화한다. 같은 월드 정의와 런을 사용하며 체력·생명·Foundation·무기 수치·체크포인트·공용 오브젝트 상태는 새로 만들지 않는다.
3. 동일한 월드 정의와 revision을 사용하는 싱글·멀티가 같은 영역 순서·지형·오브젝트·Gate 연결을 만든다.
4. `1-3`·`1-5`·`1-7`은 Turret을 파괴하지 않아도 각 시나리오의 우회·도달·상호작용 조건으로 완료할 수 있다.
5. `1-1`~`1-8`은 각각 입구·경로·회복 지점·필수 목표·출구·다음 영역 참조·mock cue 목록을 가진다.
6. 인접 영역 연결, 중복 ID, 존재하지 않는 목표/Gate 참조, 로프 사거리와 상승 경로를 자동 검증한다.
7. `1-8`은 두 Turret의 동시 Crossfire 없이 Gate Override 뒤 Lower Grid Shutdown과 Worker District Preview를 재생하고 일반 구간 종료 Checkpoint를 활성화한다.
8. 일반 구간 타이머는 `1-1`~`1-8` 사이에서 초기화되지 않고 명시적 Gate 통과 때 mock 시간을 보충한다.
9. 일반 타이머 0초는 즉시 실패가 아니라 하층부터 상승하는 붕괴를 시작한다.
10. 붕괴에 잡힌 플레이어는 입력 차단·생존 동료 자동 추적·상태 표시를 받고 다음 Gate에서 합류한다. 전원 탈락 때만 Sector 01 일반 구간을 재시작한다.
11. 기획자 지정 보스 진입은 일반 타이머·붕괴를 종료하고 잔여 시간을 폐기한 뒤 별도 보스 타이머를 시작한다.
12. 보스 타이머 0초는 Arena 붕괴를 시작하고 전원 탈락은 보스 시도만 재시작한다.
13. `1-8`의 Shutdown·Worker District Preview·일반 구간 종료 Checkpoint는 보스 배치 추정 때문에 이동하지 않는다.
14. 타이머·보충·붕괴 속도의 mock 값은 공동 플레이 뒤 수치만 교체할 수 있고 상태 흐름은 유지된다.
15. 모든 영역은 Gate 옆 패널을 가지며, 선행 목표만으로 문이 자동 개방되지 않고 패널 조작 뒤에만 열린다.
16. 각 영역의 좌우 벽과 층간 격벽은 Gate 개구부 외 경계를 충돌로 막아 로프 탄성으로 문을 우회할 수 없게 한다.
17. 열린 Gate의 포탈 trigger는 바닥 기준 문 내부 `52×62` aperture만 사용한다. 특히 `1-3` 문 위에서 로프 액션을 계속해도 영역 전이와 상태 초기화가 발생하지 않고, 플레이어 중심이 실제 문 내부로 들어오면 전이된다.

## 검증 순서

1. 영역 정의·연결 validator와 고정 회귀 fixture를 실행한다.
2. `1-1` 단위 시뮬레이션에서 Terminal → Gate unlock → Gate crossing → `1-2` 활성화를 검증한다.
3. `1-1`~현재 구현 영역을 처음부터 연속 플레이하고 영역 전환 전후 상태 digest를 비교한다.
4. 데스크톱·모바일에서 Gate 잠금/해제, 다음 목표 표시, mock cue 판독성을 확인한다.
5. 두 클라이언트가 같은 영역 완료·Gate 상태를 보고 공용 진행은 한 번만 다음 영역으로 전진하되, 각 캐릭터는 열린 문에 직접 진입한 자기 포탈 사건에서만 지정 도착 좌표와 초기화 상태로 수렴하고 원격 캐릭터가 두 영역 사이를 보간하지 않는지 확인한다.
6. 구현 작업의 병합 전 `npm test`, `npm run check`, `npm run format:check`를 실행한다. `npm test`의 current authored world 단계가 영역 연결·Gate·content boundary를 검증한다.
